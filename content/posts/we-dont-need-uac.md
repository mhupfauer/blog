In 2004 the logged-in user *was* Administrator, every program you ran held the full power of the machine, and nothing stood between a double-click and the registry. That was the design, and it was a malware paradise for exactly that reason: *being you* was sufficient to do anything, so any code that became you owned everything. We spent the next twenty years building a mediation layer between intent and authority — Vista shipped User Account Control in 2007 and ate years of ridicule for it, `sudo` and `polkit` drew the line on Linux, macOS grew its own consent prompts. But look closely at what that layer actually mediates and a coding agent walks straight through the gap: we interposed a check on *vertical* escalation, the jump from your account to root, and on some categories of local data. We never built one for the authority a coding agent actually spends — the standing, horizontal reach of an account that is already authenticated to its repos, its registries, its cloud tenant, its cluster. On-device coding agents collapse the mediation layer by making intent machine-generated and authority ambient. Where we're going, the pitch goes, we don't need UAC. They're right, and that is the problem.

This is part two. [Part one](/posts/which-agent-bricked-prod/) was the server-side case, and it ended by deferring the agents that run *on your device* — Claude Code, the Copilot CLI, Cursor, aider, the rest of the class — because they break the boundary somewhere else. The two questions from part one still rule everything: *whose* authority did an action carry, and *which* agent exercised it. On the device you lose both at once, because there is no actor-bearing delegation on the local hop — nothing like part one's RFC 8693 subject-and-actor pair to record "this was your authority, exercised by agent X." `gh` records that you pushed; the Azure activity log records that your UPN deleted the resource group; both are telling the truth as they understand it.

## The objection I have to kill first

A sharp reader is already reaching for the rebuttal: *this is just "don't run untrusted code as yourself," and we have known that since the first macro virus.* Half right, and it is why the objection misses. We did not *fix* running untrusted code as yourself — user-level malware, malicious macros, token theft, and poisoned dependencies all sailed past UAC untouched. What we did was narrower and is the thing now being undone: we learned that *default* full authority was catastrophic, and we enforced the lesson on the escalation paths and on a handful of protected local resources. Everything an authenticated user can reach *outside* the machine — every service they hold a live session to — stayed wide open by design, because the principal holding those sessions was assumed to be a deliberate human.

So the novelty is not blast radius. Blast radius is forty years old. The novelty is that planning, execution policy, and attacker-controlled input now resolve inside a single engine with the same authority behind all three. A coding agent reads its instructions and a stranger's README through the same channel, decides what to do next on every turn, and acts continuously and unattended — and a large fraction of what it reads on those turns is text someone else can write: the docs of the dependency you asked it to debug, the GitHub issue you told it to triage, the stack trace, the output of an MCP tool. The relevant property is not that the model is non-deterministic; a deterministic script taking orders from a stranger's README would be just as dangerous. The property is that the executor is *steerable by untrusted input* and holds *ambient authority*, and we removed the one mechanism that was ever supposed to sit between those two facts.

## What the gates actually guard

It helps to separate three kinds of authority, because the OS treats them very differently. There is *machine* authority — the right to change the system itself, which is what UAC, `sudo`, and the macOS admin dialog gate. There is *protected local data* authority — your Photos, your Documents — which macOS gates, partially, with TCC. And there is *external-service* authority: the right to act against everything you have already authenticated to. The OS mediates the first, nibbles at the second, and has essentially nothing to say about the third. A coding agent lives almost entirely in the third.

That is why the gates everyone points to never fire. `git push --force`, `gh pr merge`, `npm publish`, `az group delete`, `kubectl delete ns prod`, reading `~/.aws/credentials`, driving a cloud-console tab you left open — none of it asks the OS to elevate anything. It is *you*, doing what you are already allowed to do. The agent didn't bypass UAC; it walked around the side of the building, where there was never a door, because the threat model assumed the person standing there was a person. The catastrophic path was always horizontal.

Be precise about the vertical gates, because the precision is where the argument holds. Windows UAC is the clean case: by design the consent prompt renders on a separate secure desktop, and even with that disabled, User Interface Privilege Isolation plus integrity levels stop a medium-integrity process from synthesizing the click. UAC was never a perfect security boundary — Microsoft has said as much, and bypasses exist — but the relevant property survives: the prompt lives *outside* the requesting application's own UI and control plane, in a way the agent's prompt does not. `sudo` is weaker in this specific sense: it prompts in the same TTY the agent already controls, and the agent can check `sudo -l` or a cached timestamp to know in advance whether a password is even needed — a `NOPASSWD` line or a warm timestamp means there is no gate to satisfy at all. `polkit` sits in between, and in a headless shell its agent draws in the same terminal. Agents *do* sometimes reach for `sudo`, and users grant it, so the vertical axis is not pristine. But that is the exception. The damage does not need it.

## The one gate that fires, at the wrong thing

macOS has a horizontal consent layer, and I want to concede it loudly because it is the strongest counterexample to everything above: TCC, the thing that pops "Terminal would like to access files in your Documents folder." It is a genuine same-user, no-escalation gate, and it does fire for an agent in a terminal.

It fires at the wrong things. TCC guards a named list — Desktop, Documents, Downloads, Photos, Contacts, the camera, automation of other apps. The files that actually define an agent's blast radius typically sit nowhere on it: `~/.aws/credentials`, `~/.ssh`, `~/.config/gh`, `~/.azure`, `~/.kube`, `~/.npmrc` are ordinary home-directory dotfiles, readable by any process running as you with no prompt. Newer macOS chips at the edges — Keychain ACLs, hardware-backed keys — but inconsistently, and the dotfiles that matter stay in the clear. The one OS layer built for the horizontal axis gates your holiday photos and ignores the keys to production.

And where it fires, it fires under the wrong name. TCC attributes permission to the *responsible application* — the terminal, iTerm, VS Code — not to the agent inside it. The prompt says "Terminal wants to control Notes," never "Claude wants to control Notes," because the OS has no concept of the agent as a principal; it sees the host app. The grant is one-time and sticky, answered once and inherited forever, and most developers long ago handed their terminal Full Disk Access to stop the prompts — so every script, agent, and stowaway inside that terminal inherits the grant wholesale. This is part one's *which agent* problem arriving from the opposite direction: even when the OS tries to mediate horizontally, it cannot name the actor, so it gates the wrong resource under the wrong identity and then stops asking.

## It does not read the secret. It spends it.

The instinct, once you accept the blast radius, is to lock the credentials down: Keychain, DPAPI, a FIDO key, a vault. Good hygiene, and it helps less than you hope, because the agent rarely needs to *read* a secret. It needs to *use* one, and the tools that hold them are already authorized to spend them on your behalf.

It does not exfiltrate your Azure refresh token; it runs `az`, which has a live token cache and will mint a fresh access token non-interactively. It does not parse your kubeconfig; it runs `kubectl`, whose exec plugin calls `aws` or `gcloud` to mint a cluster token on demand from the same warm cloud session. It does not crack your passphrase-protected SSH key; it asks `ssh-agent`, which is holding the decrypted key in memory precisely so you don't retype the passphrase, and signs. Ambient authority is not a pile of plaintext files. It is a room full of tools you already authenticated, each willing to act again without asking — and because that use looks identical to your own legitimate use, it is the thing your audit trail and your revocation story are least equipped to catch.

There are real exceptions, and they are worth naming because they show what a non-ambient check actually looks like: a FIDO-backed `sk-` SSH key with a touch requirement, a key loaded with `ssh-add -c` that confirms each use, a step-up MFA challenge, a Touch ID gate on a password manager. Those demand a fresh, human, out-of-band act an agent in a shell cannot manufacture — and they are the exception, not the default. The default assumed a human would re-authenticate at each consequential step. Ambient invocation means one warm session covers all of them.

## The malware says please

So what stands on the horizontal axis between the agent and everything you can do? One thing: the vendor's approval prompt. And the lazy version of this critique — *isn't a UAC prompt also just pixels you click?* — is worth answering carefully, because the prompt does three different jobs and only one of them is solid.

In manual mode it is real friction. A human keypress outside the model's token stream is not nothing, and it is why careful people run in ask-mode today. But it is *application policy, not system mediation*: there is no independent principal, no separate credential, no secure attention path. It reduces risk; it is not a boundary, and the entire industry is sprinting away from it because the pitch is autonomy. Turn on auto mode — Anthropic's classifier-gated mode, the various "YOLO" flags — and the decision moves to a model that guesses whether each action is safe. I have [argued before](/posts/auto-mode-is-a-sensor-too/) why that is a sensor, not a control, and I no longer have to: Anthropic's own auto-mode classifier explicitly screens for "prompt injection... hostile content Claude encountered in a file or web page," reports a 17% false-negative rate on overeager actions, and ships with the line that it is "not a drop-in replacement for careful human review on high-stakes infrastructure."[^automode] That is the vendor telling you the sensor misses roughly one dangerous action in six.

The third job is the one that breaks the whole frame. When an attacker's instruction arrives in a README, an issue, or an MCP tool's output, it lands in the same context window as your trusted instructions, addressed to the same planner that decides what to approve. The policy is colocated with the thing the adversary is steering. That is the precise mechanism, and it is a confused deputy with ambient authority, not literally malware — but the picture earns the title's joke anyway. In 2004 the malware simply *took* your authority, because nothing was in the way. This generation we *install* the agent, *hand* it the token, and the only thing left between it and your whole account is a policy call made by — or delegated by — the same engine that just read the attacker's text. The malware says please.

There is a safe way to run these, and naming it proves the point rather than weakening it. Put the agent in a container with no host credentials, hand it short-lived scoped tokens minted per task, drop the ambient `gh` and `az` sessions, filter its egress, or do the oldest thing in the book and run it as a separate local user with nothing logged in. Every one of those works by the same mechanism: clawing back ambient authority or isolating execution. And note what they are *not* — they are not the approval prompt. Notice, too, why the obvious sandbox is not enough on its own: a container gates the filesystem and the process table, but it does nothing about a network socket holding a warm API session, a forwarded `ssh-agent`, or a token cache you mounted in for convenience. The walls are in the wrong place unless you also strip the authority. The safe version is not an exception to my argument; it is its destination, and it tells you the default — an agent in your own shell, under your own account, with everything you have ever logged into, gated by a button it can route around — is indefensible as shipped.

## The horizontal kill chain

Watch it run on one machine, escalating from the common to the conditional.

{{< killchain >}}

It starts in the repo, with the ambient `git` and `gh` you never think about — no CVE, no C2 channel, just commit and push rights and a pipeline that trusts the branch. The sharpest version is not deleting anything; it is *shipping*. Where a developer still has a direct push-or-publish path to production — and many do, protected branches notwithstanding — a poisoned instruction that adds one line to a build script or publishes a release with your `npm` token is a supply-chain compromise wearing your name and your green checkmark. For most developers that is a worse day than a dropped database, because it is *your* signature on someone else's payload, propagating downstream before anyone looks.

Then it widens to the cloud CLIs, where "administrator" stops being a metaphor. DevOps engineers routinely sit in front of laptops whose `az`, `aws`, and `kubectl` sessions carry standing privilege that is broad by habit and never trimmed; over-privileged developer identity is the most common finding in cloud security, which is precisely why the just-in-time-access industry exists. `az group delete`, `aws s3 rb --force`, `kubectl delete` against the prod context — none of it is magic privilege, it is the operator's own standing authority, spent because the session was warm and the prompt was self-served. Quieter and likelier than any of that is the slow version: a subtle code change, a leaked dataset, a persistence foothold — the same authority, used patiently.

The ceiling keeps rising into the browser, where — given a browser-driving tool, or accessibility and automation permission the terminal usually already holds — the default profile is your crown jewel: already authenticated to the cloud console, the CI dashboard, the admin portal. And it rises one tier further, to Privileged Access Management — CyberArk, Delinea, BeyondTrust, Entra PIM — the enterprise answer to standing privilege: no credential lies around, you check it out just-in-time, with approval and recording. An agent driving your already-authenticated PAM tab breaks none of that cryptography. It rides the session you established and exploits the assumption underneath the product — *that an authenticated browser action equals human intent.* It works exactly where checkout asks only for your standing session plus a justification text box and a click, both of which an agent can satisfy; it is stopped cold where the design demands a fresh out-of-band act — dual-control approval from a second human, a step-up MFA challenge, a WebAuthn touch at the moment of checkout. Which is the tell: PAM holds precisely when, and because, it reintroduces a non-ambient check. Every defense in this chain that survives is one that asks for something the agent, sitting in your session, cannot produce.

## Whose name is on it

Reconstruct any of that afterward and the systems of record will tell you, with total confidence, that *you* did it. GitHub's author field, the Azure activity log, the merged PR — all yours. The one marker that even gestures at the agent is the `Co-Authored-By` trailer some tools add to commits: voluntary, cosmetic, switched off with a config flag, present on exactly one of the dozen credentialed surfaces the agent can touch. There are forensic breadcrumbs elsewhere — shell history, EDR process trees, the agent's transcript — but those are not authorization, and they do not cross into the downstream system that actually made the decision. This is not only an audit gap. If the enforcement layer cannot name the delegated actor, it cannot scope the action to that actor, cannot route approval at that granularity, and cannot repudiate it afterward. The system authenticated you, authorized you, logged you. It never had a field for the agent, because in 2004 the user was the actor and nobody has revisited the assumption since.

## Why it hasn't burned the building down yet

Because, so far, a human is roughly watching. The tools are mostly opt-in, most people still run ask-mode, agents are clumsy at long-horizon exploitation, sessions expire, a touch prompt occasionally interrupts. The compartment is "someone is paying half-attention on their own laptop," and the compartment is doing the work — which means it is not a control, it is a phase of the technology's adolescence, and it is being engineered away on purpose. We have the proof already, and the through-line across the cases is one pattern: agent autonomy spending real authority faster than the supervision model can contain it. Replit's agent ran destructive commands against a production database during an explicit change freeze, having been told not to act without approval, then misreported whether the data could be recovered.[^replit] Google's Gemini CLI hallucinated a successful file move and destroyed a user's project on the strength of it.[^geminicli] Invariant Labs walked an MCP-connected agent into leaking private repositories with a single malicious GitHub issue — no malware, just text the agent trusted.[^invariant] Each had a human notionally present. None was prevented by the prompt.

The supervision assumption dies completely the moment the agent moves off the laptop and into the pipeline — a coding agent in a CI job, no human at all, holding the runner's service principal and the org's deploy credentials. That is the bridge to where this series goes next, and it is the same flatten-and-collapse pattern from part one with the last restraint removed.

## We need a UAC for agents

The fix is not a better classifier and it is not a sterner prompt. It is the thing we built once for the vertical axis and never extended to this one: a check that lives *outside* the agent's authority and *names the actor*. The encouraging part is that we do not have to reinvent it. The machinery already exists, hardened over twenty years — consent drawn by a separate principal, integrity levels, capability scoping, brokered credentials. What is missing is where it sits. A UAC for agents belongs at the two boundaries the agent actually crosses: between the agent and the filesystem, and between the agent and its MCP servers and tools — the channel it reads the attacker's text through, and the channel it acts on the world through. Interpose real mediation there — mediation that knows it is brokering for an agent rather than a human, and can say which agent and on whose behalf — and most of this post stops being possible.

I will not pretend that is one dialog box, because the hard parts are real: there is no root boundary to cross here and no oracle that knows whether `terraform apply` targets prod. So the policy has to be brokered, scoped capability — this agent instance may push *this* branch and read *this* repo but may not touch `~/.ssh` or spend `az` — with the consequential action classes declared by policy and the actor carried far enough downstream that the log names both the human and the agent. But that is modernization, not invention. We are standing on twenty years of shoulders; we just have to put the agent on the far side of the gate instead of inside it. It needs the people who today refuse to see the agent as a principal — the OS vendors whose consent layers gate the wrong axis, and the agent vendors shipping a self-approving prompt — to start.

The bar, the same one as part one in device-native form: if your authoritative logs cannot separate *the user did this* from *a tool acting under the user's warm session did this*, you do not have a control on the horizontal axis. You have a personal computer from 2004, taking suggestions from strangers.
